# Known Issues, Risks & Technical Debt

Found by reading the code; none were reproduced by running it. Confidence: **[C]** certain from code, **[L]** likely — depends on library behaviour or live-DB state that was not inspected.

## Security (critical)
1. **[C] No backend authentication/authorization.** Every service takes `userId`/`teamId` from the request and uses a service-role Supabase client. Anyone who can reach a port can act as any user (create/delete posts, schedule publishes to a victim's accounts, delete accounts, invite/upgrade). Files: all `services/*/src/index.ts`. CORS is `*`.
2. **[C] Hardcoded fallback encryption key** `'12345678901234567890123456789012'` in account-service, publishing-service, analytics-service (and `test-fb.js`). If `ENCRYPTION_KEY` is unset (it is **not** in the current `.env`), all tokens are protected by a key that is in the repo. Also AES-CBC without integrity check. ⚠ Don't "fix" by just setting a new key — existing tokens would become undecryptable.
3. **[C] Unauthenticated internal endpoints:** `/publish/:jobId`, `/auth/youtube/refresh`, `/analytics/event`, `/media/upload` are callable by anyone.
4. **[C] OAuth `state` kept in a process-local Map** (no TTL, lost on restart, not shared across instances); the same Map object is what authorizes which user/team gets the token.
5. **[C]** Public storage bucket: every uploaded media URL is world-readable (required for Meta/Pinterest fetch, but drafts are exposed too).
6. **[C]** Secrets hygiene: `.env` is git-ignored (good), but `cloudflared.exe` (55 MB) and scratch scripts (`test-fb.js`, `query_db.js`) sit in the root; `test-fb.js` reads real tokens from the DB. Check they contain no pasted credentials before committing.

## Functional bugs
6. ✅ **FIXED 2026-09-22 — [C] Retries never happened.** The job had no `attempts`, so the first failure was final and no notification was sent. Now the worker retries transient failures itself (3 attempts, backoff 1 min then 2 min; permanent errors like "account not connected" fail at once), notifies on the final failure, and the user can press **Retry failed** (see BUSINESS_LOGIC §5, API_MAP `POST /posts/:postId/retry`). BullMQ's own `attempts` is deliberately NOT used: in BullMQ 4.18.3 `attemptsMade` grows on every run (also after a rate-limit delay), so the worker counts failures in `job.data.failures`. Verified by `docs/dev-scripts/retry-e2e.js` (42/42).
7. **[L] Rate-limit delay path.** Worker calls `job.moveToDelayed()` and then `return`s. In BullMQ ≥ 4 the processor must `throw new DelayedError()` afterwards; otherwise the job is finalised/lock errors occur, so the "delay 1 h" may not work. Affects Facebook Reels 30/24 h, Threads 250/24 h and the 5/min limiter.
8. ✅ **FIXED 2026-09-22 (status part; the new retry endpoint adds only `publish_jobs`, no duplicate `schedules` rows).** **[C] Post never becomes `published` after a retry.** The worker requires *all* `publish_jobs` of the post to be `completed`; "Retry Publish" creates new jobs but leaves the old `failed` rows, so `every(completed)` stays false. Also, retries add duplicate `schedules` rows (timeline/calendar use `schedules[0]`).
9. **[C] Wrong account can be used / lookups crash.** publishing-service and analytics-service load the account with `.eq('user_id', post.user_id).eq('platform', x).single()` — ignores `team_id`, uses the post *author's* connection (a teammate's post fails "account not connected"), and errors when the user has two rows for a platform (the connect flow does not prevent duplicates; only the UI does).
10. **[C] Analytics never reach the UI for new data.** analytics-service inserts rows without `team_id`, but `DashboardProvider` queries `analytics` by `team_id`. Also `posts/page.tsx:655` renders analytics only when `post.status === 'scheduled'` (published posts hide them). And the insert fallback `user_id: 'unknown'` would violate the uuid type.
11. **[C] `Publish Now` on an existing post loses `contentType`** (defaults to `post`), so a Reel retried from the timeline is published as a normal post. It also uses `window.prompt` for platform selection.
12. **[C] Video with `contentType='post'`** on Facebook (`/photos`) and Instagram (`image_url`) is sent as an image URL → fails.
13. **[L] Pinterest media:** adapter uses `post.media_variants?.pinterest || post.media_url`; `media_variants` doesn't exist and `media_url` is a JSON string → invalid image URL. Video-pin cover image is a placeholder URL.
14. **[C] Facebook always posts to the first page**, Instagram to the first page with a linked IG account — no selection UI.
15. **[C] LinkedIn cannot connect for real** (mock token branch) and TikTok is fully stubbed but both appear as normal, "Connected" platforms in the UI and README.
16. **[C] Tokens expire silently.** Only YouTube refreshes. Meta/Threads (~60 d), Pinterest, LinkedIn tokens are never refreshed and the UI only warns about LinkedIn (using a field LinkedIn never sets).
17. **[C] Scheduling is not atomic**: a failure mid-loop leaves partial `schedules`/`publish_jobs` rows and already-queued jobs, and `posts.status` unchanged. It also doesn't check that an account exists for each chosen platform (failure only shows up at publish time).
18. **[C] Deleting a post doesn't remove its queued jobs** → the worker later hits "Post not found" and marks failure. *Confirmed 2026-09-21: 10 of 11 delayed jobs in `publish-queue` were orphaned (their `publish_jobs` rows are gone via cascade); they will 404 in publishing-service and fail without publishing. Also 40 failed and 31 completed jobs are retained in Redis (no `removeOnComplete/removeOnFail`).*
19. **[C] `queue_job_id` is never populated**, and no endpoint for reschedule exists (calendar Step 4 prerequisite is only half-done; `jobId == publish_jobs.id` makes it recoverable).
20. **[C] Feed cache staleness:** `feed:<team>` lives 60 s and is only invalidated on create/delete, not on status changes. *(Range/calendar queries are no longer cached as of 2026-09-21.)*
20b. **[C] `GET /api/v1/posts` (non-range) returns 500 on the current DB:** its `user:user_id(email)` embed fails ("Could not find a relationship between 'posts' and 'user_id'") because `posts.user_id` references `auth.users`. Pre-existing (initial commit). The frontend doesn't call it; the calendar range query no longer uses the embed.
20f. ✅ **FIXED 2026-09-22** — see the end of this entry. **[C] Reels/Shorts are no longer converted to 9:16 (found 2026-09-22; regression from the previous agent's uncommitted Threads change to `services/media-service/src/index.ts` `processVideo`).** Committed HEAD scaled + **padded** reel videos onto a 1080×1920 canvas (and standard videos onto per-platform canvases: instagram 1080×1350, facebook 1920×1005, youtube 1920×1080, pinterest 1000×1500, default 1920×1080). The working tree replaced all of that with `scale=min(1080|1920,iw):-2`, which keeps the source aspect ratio. Result: a landscape video uploaded as a Reel stays landscape (real data: the test post's facebook / instagram / youtube variants are 1080×608, threads 1280×720, all `content_type=reel`), so YouTube publishes it as a normal video (a Short must be vertical or square) even though the adapter still appends `#Shorts`; Instagram/Facebook reel variants are landscape too. The reel signal itself is fine (`publish_jobs.content_type='reel'`, scheduling-service and the YouTube adapter are unchanged). Side effect in the other direction: a *vertical* video posted as a standard YouTube post is no longer pillarboxed into 16:9. Fix = restore the HEAD canvas/pad logic and keep Threads as the only special case (natural aspect, width ≤ 1920, ≤ 300 s); afterwards `lib/mediaFrame.ts` (preview frames) and the reel-orientation warning in `PlatformPreviewCard` must be updated to match, and already-uploaded variants of existing posts stay landscape (media can't be edited yet).
    **Fix applied:** `services/media-service/src/videoFilter.ts` (`getVideoFilter`) restores the pad logic — reels 1080×1920 for every platform except Threads, standard videos on the platform canvas, Threads keeps its own ratio (width ≤ 1920). While restoring it, an old latent bug surfaced and was fixed: the Facebook standard canvas `1920:1005` has an odd height and made ffmpeg fail, so it is now `1920:1006`. Verified end to end with `docs/dev-scripts/media-e2e.js` (3 sample clips × reel/post × 6 platforms through the real upload endpoint, measured with ffprobe; 40/40 pass, padding geometry checked, scratch files deleted). Frontend synced: `lib/mediaFrame.ts` video frames = the canvases, the reel warning now says the video will be shown with black bars in 9:16 (never for Threads). Existing posts keep their old (landscape) variants — e.g. the 23 Sep test post.
20e. **[C] `updated_at` triggers are not effective on the live DB (verified 2026-09-21 on `posts`):** an UPDATE leaves `updated_at` unchanged, so it cannot be trusted as "last modified" (e.g. `posts.updated_at` did not move when scheduling set `status='scheduled'`). Code that needs it must set it explicitly — `PATCH /api/v1/posts/:id` does. Likely affects the other tables that rely on `trigger_set_timestamp` (schedules, publish_jobs, social_accounts) too; not yet checked.
20d. **[C] Live-DB RLS drift (verified 2026-09-21 by running queries as the browser user):** `schedules`, `publish_jobs`, `notifications` and `analytics` return **0 rows** to the logged-in owner although all 7 / 7 / 31 / 2 rows are theirs (`posts`, `social_accounts`, `team_members` are fine). Effects: timeline shows `created_at` instead of the scheduled date, job status/errors never appear, sidebar notifications stay empty, analytics never render, Realtime for those tables never fires. Fix: `supabase/migrations/20260921000000_restore_read_policies.sql` (SELECT-only, own rows; must be applied manually in the SQL editor). Teammates still cannot see each other's rows (policies are user-scoped, not team-scoped).
20c. **[C] `publish_jobs.queue_job_id` is missing on the cloud DB** (verified 2026-09-21) — migration `20260919000000` was only ever applied to a "local" instance, if at all.
21. **[C] Threads:** analytics needs `threads_manage_insights` (not requested); text match to posts is fragile; byte-vs-character limit; no UI counter; no token refresh.
22. **[L] Team bootstrap & RLS.** First-login team creation from the browser needs INSERT policies that migrations don't define; `team_members` policies are self-referential (possible recursion error); teammates lose visibility of others' `publish_jobs`/`schedules` because those RLS policies are still user-scoped. Verify against the live DB.
23. **[C] Team invite** uses `auth.admin.listUsers()` with default pagination (first page only) and only works for already-registered users; `plan`/`role` bodies are not validated.
24. **[C] Free-plan post cap** is 500 with a "for testing" comment; the real value was never set.
25. **[C] `pinterest_published_pins` PK is `post_id`** → a second Pinterest publish of the same post fails insert (result not checked, so it fails silently).
26. **[C] Analytics `shares` is overloaded** across platforms; comments/clicks/replies are mapped into it.
27. **[C] Worker concurrency is BullMQ's default (1)** and the worker blocks on the HTTP call; an Instagram/Threads video poll (up to 2 min) or YouTube upload (entire file in memory) stalls every other publish. The worker's `fetch` has no timeout.
28. **[C] media-service** buffers entire uploads in memory (`multer.memoryStorage`, no size limit), runs ffmpeg for each platform in parallel (`Promise.all`), and the storage `postId` is a random UUID unrelated to the real post id (orphaned files are never cleaned).

## Deployment / config

30. **[C] `.env.example` is stale** (missing Facebook, Threads, Twitter, LinkedIn, Pinterest, Upstash, encryption, `API_BASE_URL`, `NEXT_PUBLIC_*`).

34. **[C] Migration hygiene:** two empty duplicate "initial_setup" migrations; `scratch_init.sql` stray; later migrations untracked; code depends on columns with no migration.
35. **[C]** Tracked compiled `dist/` for services will drift/conflict on every rebuild.
